# SuperDoc: что можно украсть, а что нет

Разбор `/home/artem/Документы/artemius125/superdoc-main` против наших семи вопросов и
списка отказов из `BUILD_PLAN.md` (Ф14). Метод: код, а не документация — маркетинговые
формулировки из `docs.superdoc.dev` проверены построчно.

Первое, что важно понять: у SuperDoc **два** AI-инструментальных слоя, не один.

| | `legacy`/`intent` (MCP по умолчанию) | `core` (то, что описывает документация) |
|---|---|---|
| Инструментов | 9 (`superdoc_get_content`, `superdoc_edit`, `superdoc_format`, `superdoc_create`, `superdoc_list`, `superdoc_comment`, `superdoc_track_changes`, `superdoc_search`, `superdoc_mutations`) | 2 (`superdoc_inspect`, `superdoc_perform_action`) |
| Где | `apps/mcp/tools/catalog.json:1-9` (`"toolCount": 9`), имена — `catalog.json:7,75,328,844,1007,1249,1359,1437,1575` | `apps/mcp/src/tools/core.ts:2-3`, действия — `packages/sdk/langs/node/src/embedded-prompts.generated.ts:8-9` |

Задание архитектора («40 действий», `blockOffset/blockLimit`, `MATCH_NOT_FOUND`,

## 2. Адресация и стрелка ID vs offset

Селекторы (`embedded-prompts.generated.ts:9`, блок «Selector shapes») и их резолвинг —
`packages/sdk/langs/node/src/agent/doc-snapshot.ts:829-947` (`resolveSnapshotSelector`):

- `{kind:"nodeId", nodeId}` — прямой id
- `{kind:"ordinal", ordinalKind:"bodyParagraphOrdinal"|"paragraphOrdinal"|"headingOrdinal"|
  "tableOrdinal"|"listOrdinal"|"sectionOrdinal"|"blockOrdinal", value:N}` — счёт с разными
  базами (важно: `paragraphOrdinal` считает НЕ все абзацы, а видимые непустые —
  `doc-snapshot.ts:833-843`)
- `{kind:"tableCell", tableOrdinal, rowIndex, columnIndex}`
- `{kind:"textSearch", terms, match:"all"|"any", occurrence, caseSensitive, nodeTypes}` —
  это ближайший аналог нашего `find.by_text`/`find.locate`, но с явным `occurrence` (какое
  по счёту совпадение брать) вместо нашего «взять единственный лучший»
- `{kind:"relative", position:"before"|"after", target:selector}` — сосед селектора

Неоднозначность — `AmbiguousSelectorError` (`doc-snapshot.ts:813-822`): бросается со
списком РЕАЛЬНЫХ кандидатов (`{nodeId, description}[]`), не просто «не найдено». Модель
получает готовый список, а не гадает.

**Ревизия** — НЕ хэш содержимого. Это монотонный счётчик на инстанс редактора
(`packages/super-editor/src/editors/v1/document-api-adapters/plan-engine/revision-tracker.ts:
15-28`), инкрементируется на каждой транзакции ProseMirror. `REVISION_MISMATCH`/
`STALE_REVISION` ловят «кто-то помимо меня поменял документ между чтением и записью» —
это staleness-check, НЕ проверка корректности содержимого.

**Применимо к нам?** Слабо. Ревизии решают проблему конкурентного/многошагового доступа
к id из ПРЕДЫДУЩИХ ходов агента через несколько раундов диалога — у нас документ
однопоточный, id не переживают между вызовами: `_run_clusters` пересчитывает `doc_map()`
перед КАЖДЫМ кластером (`docx_editor/edit.py:601` — `find.fragment(doc_map(doc, idx), ...)`
внутри цикла `for cluster_ids in clusters`). У нас структурно нет случая «использовать id
из прошлого хода» — ревизия ловила бы проблему, которой у нас физически не бывает.

## 3. Чтение без усечения

Подтверждаю `blockOffset`/`blockLimit` — реальны, не только в документации:
`packages/sdk/langs/node/src/agent/doc-snapshot.ts:242-251` (комментарий в коде):

> «a 600-block / 38-page doc produces a ~58k-token full snapshot, so a reader pulls a
> bounded slice (e.g. offset 0, limit 40) per window instead of the whole thing.
> `counts.blocks` / `blocks[].ordinal` still reflect absolute positions»

Ключевая деталь: `counts.blocks` (общее число) отдаётся ВСЕГДА, даже когда вернули только
окно — окно никогда не выглядит как «это весь документ» (`doc-snapshot.ts:333-353`,
путь `countsOnly`, и далее `countsFromInfo` собирается независимо от `blockLimit`). Плюс
`omitEmptyBlocks`/`dropTextPreview` — управляемое, документированное сжатие payload'а
(`doc-snapshot.ts:252-265`), не порча текста.

**Применимо к нам, и это подтверждает уже принятое решение, не новая идея.** Наш собственный
Ф12 нашёл ровно ту же болезнь наоборот: `render()` резал абзац на 300-м знаке ПОСРЕДИ
слова и НЕ помечал этого — модель честно копировала обрубок в `old`, находка
BUILD_PLAN.md:578-586. Пункт уже стоит в очереди («убрать усечение в render»). SuperDoc не
даёт новой техники здесь — он даёт независимое доказательство, что «окно с явным счётчиком,
без слепого обрезания» — это отраслевой стандарт, а не наша самодеятельность. Это не меняет
объём работы, только подтверждает приоритет уже открытого пункта Ф12.

## 4. Типизированные коды отказа

Два почти параллельных enum'а (потому что два слоя вызывающих — их CLI и их
document-api):

- `ReceiptFailureCode` — 45 значений, `packages/document-api/src/types/receipt.ts:17-71`
  (`NO_OP`, `INVALID_TARGET`, `TARGET_NOT_FOUND`, `MATCH_NOT_FOUND`, `AMBIGUOUS_MATCH`,
  `REVISION_MISMATCH`, `STALE_REVISION`, `PLAN_CONFLICT_OVERLAP`, `CROSS_BLOCK_MATCH`,
  `SPAN_FRAGMENTED`, `CAPABILITY_UNAVAILABLE`, …)
- `CliErrorCode` — 55 значений, `apps/cli/src/lib/errors.ts:1-62`, во многом дублирует
  первый плюс сессионные/CLI-специфичные коды.

Каждый ответ действия — `{status:'ok'|'partial'|'failed', errors:[{code, message,
recovery?}], nextStep?}`. Что интересно — не только код, иногда КОД УЖЕ ПРЕДЛАГАЕТ
исправление: при провале `replace_text` по обычному блоку код сканирует ячейки таблиц и
если находит совпадение там — кладёт готовый альтернативный селектор прямо в
`recovery:{kind:'retry', selector: cellHint.selector}`
(`packages/sdk/langs/node/src/agent/actions.ts:4426-4440`). Это код, делающий часть работы
восстановления сам, а не просто описывающий проблему.

Но сам ЦИКЛ восстановления — не код: `nextStep`/`errors[].message` читает модель на
следующем ходу и решает, что делать (`embedded-prompts.generated.ts:9`, «RECEIPTS ARE
THE TRUTH… read errors/nextStep/revertHint, adjust, retry (up to 3 attempts)»). Типизация
здесь работает не как автомат, а как более узкая подсказка модели — почти всё
восстановление остаётся её работой.

**Применимо к нам?** Средне-слабо, и вот почему в лоб это не стоит копировать. У типизации
кодов есть смысл, когда КОД ветвится по ним (несколько разных вызывающих: их CLI, MCP,
тесты, plan-engine). У нас единственный потребитель текста ошибки `patch.validate` —
Редактор-модель внутри одного ретрая в `_apply_ops` (`docx_editor/edit.py:447-455`), и
измерено (Ф5), что модель читает русскую прозу нормально. Ввести enum кодов НАД строкой
ничего не изменит в поведении модели — она всё равно должна ПРОЧЕСТЬ, что не так; код у нас
и так уже ветвится ровно на бинарном «err is None / not None». **Единственный кусок этой
идеи, который стоит взять — не таксономия кодов, а паттерн «код сам предлагает конкретную
альтернативу» (см. п.7a ниже), не сама типизация.**

## 5. Верификация правки: код, но узкий, не семантический

Это самая важная находка раздела, и она режет в обе стороны.

`evaluateChecks` (`packages/sdk/langs/node/src/agent/actions.ts:1139-1191`) — набор
проверяемых кодом типов: `block-count-delta`, `comment-count-delta`,
`tracked-change-count-delta`, `revision-changed`, `block-text-contains`, `table-shape`,
`list-item-count`. Все считаются по снимку до/после (`DocumentSnapshot`), НИ ОДНА модель в
этом слое не участвует — верификация действительно детерминирована.

Но для БОЛЬШИНСТВА действий единственная проверка — `revision-changed`
(`revisionVerification`, `actions.ts:1003-1009`): просто «счётчик ревизии изменился»,
то есть «что-то произошло». Используется как единственный чек в добром десятке мест —
например `actions.ts:1507,1528,1682,1826,2075,2143`. Это буквально наш старый баг «old !=
new ⇒ done» — только у них он даже не про текст, а про факт ЛЮБОЙ транзакции.

Единственное реально сильное место — `replace_text`
(`packages/sdk/langs/node/src/agent/actions.ts:4479-4490`): код аналитически вычисляет
ОЖИДАЕМЫЙ текст блока после замены (`planned.reduceRight((text, span) => text.slice(0,
span.start) + span.replace + text.slice(span.end), block.text)`), затем после реального
применения читает блок заново и требует **байтового равенства** `postBlock.text ===
expected`. Это настоящая детерминированная постусловная проверка «движок сделал именно то,
что я посчитал», а не просто «apply() не бросил исключение».

**Что это значит для нас, честно:**

- Семантической проверки («это ли просил пользователь») у SuperDoc **нет вообще** ни в
  одном месте этого файла. Всё смысловое суждение остаётся следующему ходу
  вызывающей LLM, которая читает receipt. У нас есть отдельная роль-модель Проверяющий,
  которая именно это и делает — и измерено (Ф5: 4/4 верных вердикта на живых кейсах,
  включая «сделано наоборот»). **Мы решаем задачу, которую SuperDoc не решает вовсе** — это
  не наш пробел относительно них, а наоборот.
- Их «revision-changed»-проверка НЕ поймала бы наш собственный провал 1 из живого прогона
  (модель вставила `[CLS]` вместо `[SEP]`, BUILD_PLAN.md:397) — revision изменилась бы
  ровно так же, как при правильной замене. У них эту ошибку тоже поймал бы только
  следующий ход модели, если бы вообще заметила.
- Но их паттерн для `replace_text` (аналитически вычислить ожидаемый текст → сверить с
  фактическим байт-в-байт) — это **дешёвая, годная идея, которую мы не делаем и должны**.
  См. п.7a.

## 6. Батчинг и атомарность

`superdoc_mutations` (`apps/mcp/tools/catalog.json:1575` и далее): несколько шагов
(`text.rewrite`/`text.insert`/`text.delete`/`format.apply`/`assert`) в одном вызове,
`"atomic": true` обязателен, «All steps succeed or all fail; no partial application»
(из описания тула). Пересекающиеся по тексту шаги отклоняются ДО применения кодом ошибок —
`PLAN_CONFLICT_OVERLAP` (описание тула прямо предупреждает: «Do NOT create two steps that
target overlapping text in the same block… Overlapping steps fail with
PLAN_CONFLICT_OVERLAP»).

**Это независимо найденная нами же идея, не новая.** Наш `_overlaps`/`_shift_written` в
`docx_editor/edit.py:336-390` делает ровно то же самое для операций одного батча — отклоняет
операцию, если её диапазон пересёкся с тем, что только что записала более ранняя операция
ТОГО ЖЕ батча (найдено самостоятельно в Ф12, «дефект 2»). Совпадение подтверждает, что
решение верное, но ничего нового не даёт — мы это уже сделали.

Гранулярность отличается по КОНСТРУКЦИИ инструмента, не по силе: у них атомарность — на
уровне явного списка `steps[]`, который собирает вызывающая модель. У нас — на уровне
целой пользовательской правки (один снимок, один Проверяющий, один откат — `edit.py:
504-539` `_finish`), а кластеризация ВНУТРИ неё (Ф11) не дробит транзакцию, только вызовы
Редактора. Оба решения соответствуют одному и тому же принципу («правка либо целиком, либо
откат»), просто на разных исторически естественных для каждой архитектуры уровнях.

## 7. Что стоит взять — по силе, конкретно

### Сильное — стоит сделать

**a) Аналитическая постусловная проверка для `replace_text`/`set_text`/`replace_all`,
БЕЗ модели.** Прямая копия идеи из `actions.ts:4479-4490`. Сейчас `patch._op_replace_text`
(`docx_editor/patch.py:258-270`) вычисляет `span`, режет раны и доверяет, что результат
верен, потому что код «должен» быть правильным — единственная страховка от порчи текста
(включая класс багов Ф12 «операция бьёт по выводу предыдущей операции того же батча») —
это Проверяющий-модель, и BUILD_PLAN сам это признаёт: «Заметил 5 раз из 5… но это везение,
а не механизм» (BUILD_PLAN.md:576). Конкретное изменение (укладывается в правило «минимум
кода», ~8-10 строк, один файл):

```python
def _op_replace_text(doc, idx, op):
    el = idx[op["id"]]
    full = _ptext(el)
    span = _flex_span(full, op["old"])
    ...
    expected = full[:span[0]] + op["new"] + full[span[1]:]
    _replace_span(el, span[0], span[1], op["new"])
    if _ptext(el) != expected:
        raise ValueError(f"...")  # инвариант 6: громкая ошибка, не try/except
    return f"..."
```

То же для `_op_set_text` и `_op_replace_all` (там `expected` считается на каждый абзац
отдельно). Это прямой код-ответ на находку Ф12 «Разностная проверка порванных слов, без
словаря» — тот же пункт плана, тот же список, но проверка сильнее и проще предложенной там
альтернативы (словарный подход там же явно отвергнут как вредный). Не заменяет
Проверяющего — ловит другой класс ошибок: не «модель написала не то по смыслу», а «код
после мутации получил не то, что сам же спланировал».

### Среднее — не обязательно, но дёшево, если делать заодно

**b) Код сам предлагает альтернативу при провале поиска**, а не только описывает проблему
(`actions.ts:4426-4440`, table-cell hint). У нас похожая ситуация: когда `find.by_text`
внутри `_resolve` не находит совпадений ни для одного якоря/цитаты, мы уже вызываем
`find.locate` как запасной путь (`edit.py:_resolve`, комментарий `docx_editor/find.py:67-94`)
— то есть код УЖЕ ищет альтернативу, просто это происходит на уровне резолва адресов, а не
на уровне текста ошибки валидатора при попытке `replace_text`. Разница в том, что у
SuperDoc это происходит и внутри самой мутирующей операции, когда она уже провалилась (не
только на этапе поиска цели). Небольшой выигрыш, не приоритет.

### Слабое — осознанно не делать, и вот почему

**c) 40-действийный каталог как образец «сколько операций нужно».** Их 40 действий стоят
на движке уровня ProseMirror + полноценный конвертер OOXML — каждое действие месяцы
разработки под капотом. Копирование ЧИСЛА или ИМЁН действий без движка ничего не даёт;
Ф15 у нас уже собирает реальный список недостающих операций от измеренных отказов
(`set_format`, сноски, поля), а не от чужого каталога — это правильный источник
приоритета, чужой список — нет.

**d) Типизированные коды ошибок enum'ом.** Разобрано в п.4 — у SuperDoc это оправдано
множеством РАЗНЫХ вызывающих одного и того же кода ошибок (CLI, MCP, тесты, plan-engine).
У нас один потребитель — модель внутри одного ретрая, читает прозу нормально (измерено).
Вводить таксономию — абстракция с одним вызывающим, прямое нарушение CLAUDE.md.

**e) Ревизии / оптимистическая конкуренция (`REVISION_MISMATCH`).** Решает проблему,
которой у нас структурно нет (см. п.2) — одиночный синхронный процесс, id всегда
пересчитываются заново перед каждым кластером. Внедрение было бы абстракцией под
несуществующий сценарий.

**f) «Receipts with pre/post evidence and verification» как маркетинговая формулировка.**
Проверено — реальность у́же заявленного: верификация почти везде значит «что-то изменилось»
(`revision-changed`), не «изменилось ПРАВИЛЬНО». Наш Проверяющий решает задачу более
высокого порядка (семантика), которую SuperDoc не решает вовсе. Это не значит, что наш
подход надёжнее — модель-судья тоже ошибается (наши собственные ложные вердикты, Ф11 таблица:
«2 → 0», «2 → 1»), но у SuperDoc для СРАВНИМОГО класса ошибок (правка попала не туда по
смыслу, при формально валидной мутации) защиты просто нет вовсе. Наша архитектура здесь
не позади — читать это как повод что-то менять не нужно.

## Задача 2: можно ли прогнать SuperDoc на наших двух корпусах

**Нет, не в разумное время — останавливаюсь по таймбоксу, как и просили.**

Проверено по факту, не предположено:

1. **В окружении нет `node` и нет `pnpm`** (`which node`/`which pnpm` — пусто; есть только
   изолированный `~/.local/bin/npm` без самого node рядом).
2. Репозиторий — pnpm-монорепо на 30+ пакетов (`pnpm-workspace.yaml`: `apps/*`,
   `packages/**/*`, `shared/*`, …), `pnpm-lock.yaml` — 49 197 строк / 1.7 МБ.
3. AI-агент из `examples/ai/core-actions-agent/` (единственный готовый headless-пример,
   без браузера — подтверждено, `agent.mjs`/`agent.py` открывают документ и работают в
   консоли) требует **не просто `npm install`**, а собранный бинарник CLI:
   `SUPERDOC_CLI_BIN=<repo>/apps/cli/dist/index.js` (`examples/ai/core-actions-agent/
   README.md:16-19`), потому что SDK — не сам движок, а клиент, который спавнит CLI как
   отдельный процесс-«document engine» (`apps/docs/ai/agents/llm-tools.mdx:9-15`, диаграмма
   SDK↔CLI). Сборка `apps/cli` тянет за собой `document-api`, `super-editor`,
   `layout-engine` и, вероятно, ещё несколько пакетов транзитивно — это не «маленький
   скрипт», а полноценная сборка нескольких TypeScript-пакетов монорепо.
4. **Провайдер захардкожен на OpenAI.** `agent.mjs:69` и `agent.py` создают `new OpenAI()`/
   `OpenAI()` без указания `baseURL` — по умолчанию это `api.openai.com`, модель по
   умолчанию `gpt-5.4` (`agent.mjs:14`, `agent.py:20`, переопределяется `OPENAI_MODEL`).
   Официальные SDK `openai` для Node/Python ОБЫЧНО читают `OPENAI_BASE_URL` из окружения
   сами (это может сработать с нашим aitunnel.ru-эндпоинтом без правки кода примера), но
   этого нигде в самом репозитории SuperDoc не проверено и не гарантировано — а другой,
   более низкоуровневый пакет (`packages/ai/src/ai-actions/providers/ai-providers.ts:129,
   187`) действительно поддерживает произвольный `baseURL`, но это ДРУГОЙ, непубличный AI-слой
   продукта SuperDoc (их собственные фичи в редакторе), не тот, что используют примеры
   агента через `@superdoc-dev/sdk`.
5. Даже если бы точка 4 решилась одной переменной окружения, `superdoc_perform_action` —
   это вызов инструмента (`tools` в `chat.completions.create`) с энумом на 40 действий и
   сложной схемой аргументов на каждое — надёжность tool-calling у gemma-4-26b на схеме
   такого размера не проверена и по нашему же опыту (Ф5: модель кладёт посторонний
   примитив в `ops` даже на нашей заметно более простой 10-операционной схеме) есть основания
   ожидать проблем.

**Итог**: блокер — не провайдер (это, возможно, решаемо переменной окружения), а полное
отсутствие рантайма (node/pnpm) и необходимость собрать document-engine CLI из нескольких
взаимозависимых TS-пакетов монорепо. Это явно превышает «rutinный `npm install` + маленький
скрипт» из таймбокса задания. `pnpm install` не запускал. Если это когда-нибудь понадобится
всерьёз — минимальный путь: поставить node+pnpm, собрать `apps/cli` по их же `README.md`
сборочным командам (не исследовано глубже — вне таймбокса), и ТОЛЬКО ПОТОМ десятиминутным
тестом проверить, подхватывает ли `openai`-клиент `OPENAI_BASE_URL`/`OPENAI_API_KEY` из
`.env` без правки `agent.mjs`. Сами наши документы никуда не отправлялись.
