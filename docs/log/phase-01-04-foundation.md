# Фазы 1–4 — каркас, патч и валидатор, правила, поиск

Закрыто целиком. Первая рабочая версия конвейера: разбор документа,
применение патча с валидацией, детерминированные типографские правила,
подстрочный/regex-поиск якорей. Все пункты ниже — с демо и assert'ами
(см. `examples/parse_demo.py`, `patch_demo.py`, `rules_demo.py`, `find_demo.py`).

### Ф1. Каркас
- [x] `parse.py` перенесён из прошлого проекта как есть — проверить, что
      `index/doc_map/render` работают на `Архитектура_ColBERT.docx`
      (116 блоков, 0 таблиц, все `Normal`).
- [x] `server.py`: пять эндпоинтов, `/edit` пока возвращает поток из одного
      события-заглушки. Веб-интерфейс открывается, документ грузится,
      превью рисуется, скачивание отдаёт валидный файл.
- [x] `examples/run_all.py` — параллельный тихий раннер демо, печатает
      только упавшие. Не больше 40 строк.

### Ф2. Патч и валидатор
- [x] `patch.py`: `validate(blocks, op, doc) -> None | текст ошибки` и
      `apply(doc, idx, op) -> описание`. Валидация ДО применения:
      несуществующий id, `old == new`, `old` не найден в блоке, неизвестный
      стиль (в ошибку — список доступных стилей документа).
- [x] Операции из контракта выше, кроме `normalize` (она в Ф3).
      Правка текста — через раны, форматирование абзаца сохраняется.
- [x] Демо: каждая операция применяется; каждый вид невалидного патча
      отбивается валидатором с внятным текстом.

  Находка: `validate` в итоге принимает три аргумента — `(blocks, op, doc)`,
  а не два. Причина: список «доступных стилей абзацев» для ошибки
  `set_style` должен браться из `doc.styles` (полный каталог стилей,
  определённых в документе), а не из `blocks` — там только стили, УЖЕ
  применённые к каким-то абзацам. Проверено на реальном документе:
  `Архитектура_ColBERT.docx` использует только `Normal` во всех 116
  абзацах (см. Ф1), но в `doc.styles` определён `List Paragraph` (и НЕТ
  `List Bullet`) — без доступа к `doc` эта проверка невозможна в принципе.
  Контракт-строка выше в этом файле поправлена соответственно.

  Ревью архитектора нашло три дефекта, все починены: (1) `_ptext`/
  `_replace_span` ходили только по ранам верхнего уровня (`r_lst`) — текст
  внутри `w:hyperlink` выпадал, из-за чего `apply` видел офсеты, не
  совпадающие с `p.text` (то, что видит `validate`), и молча портил абзац;
  теперь обход через `p_el.iter(qn("w:r"))`, плюс громкая ошибка при
  недостижимом отрицательном смещении. (2) `insert_after` с несуществующим
  стилем проходил `validate` и падал `KeyError` в `apply` — вынесена общая
  проверка стиля `_style_error`, теперь зовётся и из `set_style`, и из
  `insert_after`. (3) `create_table` строил таблицу без рамок (в контракте
  нет поля `style`, а из именованных стилей часто есть только `Normal
  Table`) — рамки теперь ставятся всегда прямо в XML (`_add_borders`,
  `w:tblBorders`). Демо дополнено тремя проверками (гиперссылка, плохой
  стиль в `insert_after`, `w:tblBorders` в XML), все падают при регрессии.

### Ф3. Правила без модели

Числа ниже замерены архитектором на `Архитектура_ColBERT.docx` — это
приёмочные значения, а не ориентиры.

- [x] `rules.py`: `typography` — три правила по всему документу:
      - пробел перед пунктуацией: любой пробельный, включая U+00A0
        (в документе 6 мест перед двоеточием, и все шесть — именно U+00A0,
        обычных нет ни одного; плюс 1 место перед закрывающей скобкой);
      - пропущенный пробел после точки между предложениями. Правило:
        **слева буква ЛЮБОГО регистра, справа заглавная**; от ложных
        срабатываний защищает запрет цифр по обе стороны от точки, а не
        регистр. Так надо, потому что из трёх случаев в документе
        («в RAG.Усредненный», «процесс.Исследователи», «напрямую.В основе»)
        первый имеет слева ЗАГЛАВНУЮ `G`, и правило «слева строчная»
        пропустило бы треть случаев молча. Ложные срабатывания здесь —
        только десятичные числа (`4.2`, `0.4448`), их и отсекаем;
      - невидимые U+2060/U+200B/U+FEFF/U+00AD — вырезать. В документе их
        ноль, живого случая нет: демо для этого правила — на синтетике.
- [x] `quotes` — прямые кавычки в ёлочки (в документе 22 прямых при 13
      парах уже готовых ёлочек; вложенных кавычек внутри ёлочек нет).
- [x] Демо на реальном `Архитектура_ColBERT.docx`: после `typography`
      не осталось ни одного пробела перед пунктуацией и все 3 слипшихся
      предложения разделены, при этом 6 десятичных чисел (`4.2%`, `0.4448`,
      `0.4436`, `8.8`, `36.2%`, `6.7%`) не тронуты; после `quotes` прямых
      кавычек 0, а 13 исходных пар ёлочек целы.

  Находка: `rules.py` импортирует `_ptext`/`_replace_span` из `patch.py` (не
  дублирует их), а `patch.py` вызывает `rules.typography`/`rules.quotes` из
  `_op_normalize` — прямой импорт на верхнем уровне модуля дал бы цикл, поэтому
  импорт `rules` внутри `patch._op_normalize` сделан ленивым (внутри функции).
  Числа архитектора (7 пробелов = 6 U+00A0 перед `:` + 1 перед `)`; ровно 3
  слипшихся предложения теми же тремя строками; 6 десятичных чисел встречаются
  по одному разу; 22 прямых кавычки, 13 исходных пар ёлочек) перепроверены на
  реальном файле до написания кода — совпали ровно, расхождений нет.

### Ф4. Поиск

Ставка «поиска подстрокой хватит» проверена архитектором на всех 20
правках: якорь нашёлся у каждой, провалов ноль — эмбеддинги не нужны.
Но качество якоря решает всё: обобщённый термин даёт мусор («MaxSim» →
25 блоков из 116), а дословная цитата из формулировки правки схлопывает
выборку до одного-четырёх («размерностью m × n» → 1, «ColBERT-Att» → 4,
«Эффективность архитектур: Сравнительный анализ» → 1). Отсюда требование
к Навигатору в Ф5: якорь — самая специфичная ДОСЛОВНАЯ цитата из текста
правки, а не термин своими словами.

- [x] `find.py`: `by_text(blocks, needle)`, `by_regex(blocks, pattern)`,
      `first_mention(blocks, term)` (для «расшифруй при первом упоминании»),
      `outline(blocks)` (заголовки + первые слова абзацев верхнего уровня,
      для контекста Навигатора), `fragment(blocks, ids, around=1)`.
- [x] Демо: фикстура из 20 наборов якорей (по одному на каждую правку) —
      для каждого поиск находит непустой набор блоков, и он не больше 20.

  `outline`: в приёмочном документе заголовков нет вовсе (все 116 абзацев
  стилем Normal — см. Ф1), поэтому оглавление устроено как id + обрезанный
  до 20 знаков префикс текста для обычных абзацев (Heading*/Title — целиком,
  на будущее для других документов). На `Архитектура_ColBERT.docx` даёт
  2972 знака на 116 блоков — заведомо укладывается в промпт Навигатора
  (~300 токенов по бюджету конвейера).

  Находки по ходу фикстуры (20 якорей из `Правки_ColBERT_20.md`, все
  проверены на реальном `Архитектура_ColBERT.docx`):

  1. В документе U+00A0 встречается не только перед пунктуацией (это уже
     фиксировала Ф3), а вообще между случайными словами середины
     предложения — например `Оператор\xa0$\top$\xa0представляет`,
     `как\xa0и,`, `секундами\xa0)`. Дословная цитата из правки, набранная
     обычными пробелами, не матчится как подстрока, если задевает такую
     границу. Якоря для правок 1, 2 и 17 пришлось обрезать ДО первого nbsp
     в цитате, а не после — иначе `by_text` возвращает пустой список на
     формально «дословной» цитате.

     Ревью архитектора замерило масштаб точно: **61 из 116 абзацев
     содержат U+00A0 внутри предложения, 147 вхождений всего** — это
     большинство документа, а не редкая ловушка, и она бьёт дважды:
     в якорях Навигатора и в поле `old` операций `replace_text`/
     `replace_all`. Промптом не лечится — модель не видит разницы между
     обычным пробелом и U+00A0 в тексте, который ей показывают. Починено
     в коде, в одном месте: `find._flex_span(haystack, needle)` — сначала
     точный `str.find` (быстрый путь, точные совпадения не меняются),
     и только при промахе needle режется по пробельным разрывам
     (`re.split(r"\s+", needle)`) и собирается в regex, где любой такой
     разрыв матчится с любым другим (`\s` в Python уже покрывает U+00A0).
     Публичный `find.flex_find` отдаёт индекс начала; `_flex_span` — ещё и
     конец РЕАЛЬНОГО совпадения, а не `start + len(needle)`: разрыв в
     документе может быть длиннее или короче того, что в needle.

     `by_text` использует `flex_find`. `patch.validate` (проверка «текст
     не найден» для `replace_text`/`replace_all`) и `patch._op_replace_text`/
     `_op_replace_all` (реальное вычисление спана для замены) используют
     ОДНУ и ту же `_flex_span` из `find.py` — не дублируют её и не могут
     разойтись, это именно тот класс бага, что уже портил гиперссылки в Ф2.
     Демо: `patch_demo.test_replace_text_tolerates_nbsp` — абзац
     `"слово\xa0слово синее небо."`, `old` набран обычным пробелом,
     результат проверен целиком (не только начало), плюс отдельно проверено,
     что точное совпадение (быстрый путь) не сломано; `find_demo.
     test_by_text_tolerates_nbsp` — та же цитата про `Оператор`, что и в
     примере архитектора, находит `p31` через обычные пробелы.
  2. Формулы — отдельная ловушка: правка 16 цитирует «размерностью m × n»
     (юникодный знак умножения, как выглядит в размеченном тексте правки),
     а в документе это `$m \times n$` (сырой LaTeX-макрос, буквально
     обратный слэш и `times`). Подстрокой это не совпадает никогда. Якорь
     для правки 16 взят из текста ДО формулы («матричных умножений
     MaxSim»), не из самой формулы.
  3. У трёх правок из 20 в тексте самой правки нет ни одной дословной
     цитаты документа — это не промах `find.py`, а честная граница метода:
     - правка 6 (кавычки в ёлочки) — глобальное типографическое правило,
       оно и не должно идти через `find`: Навигатор называет `rule`, код
       применяет его по всему документу (см. «Конвейер» — правки типа
       `rule` идут мимо Редактора);
     - правка 9 («заголовок документа») — правка по позиции, а не по
       тексту: цель — первый блок документа, а не что-то, что можно
       процитировать;
     - правка 15 (вложенные характеристики в списке) — это уже описанный
       выше в «Известных рисках» невыполнимый случай (в документе нет
       списков вообще); отсутствие цитаты — ещё один взгляд на ту же
       находку архитектора, не новая проблема.
     Демо фиксирует именно эти три номера явным `assert`, чтобы если
     список изменится при доработке — это было явным сигналом регрессии,
     а не тихо пропавшей проверкой.
