# Фазы 8–10 — находки первого приёмочного прогона

Закрыто целиком. Разбор результата Ф7 (20/20, done 6 / failed 12 /
rolled_back 2) архитектором дал пять находок, и отдельно — сравнение
просмотрщика с LibreOffice на показе владельцу вскрыло структуру
документа (Н19, Н20), а сам показ — обрыв потока `/edit` через
туннель и дыру в авторизации `/logs`.

### Ф8. Находки приёмки (по порядку важности)

- [x] **Обрезание абзаца проходит как `done` — единственная найденная ложь
      отчёта.** Правка 18 (`p35`): модель выдала `set_text`, укоротив абзац
      с 456 до 332 знаков и оборвав последнее предложение буквальным «…»
      («…winner-takes-all) карди…»). Смысловая часть правки сделана верно,
      поэтому Проверяющий сказал `ok`, а машинная сверка «содержимое
      изменилось» такое не ловит по устройству. Это потеря текста, выданная
      за успех. Чинить двумя независимыми слоями:
      1) детерминированно в `patch.validate` — запретить `set_text`/
         `replace_text`, где `new` оканчивается многоточием, а `old` нет
         (в приёмочном документе таких абзацев 0, ложных срабатываний нет);
      2) показывать Проверяющему длины: в диффе к каждому блоку добавить
         «было N знаков, стало M» — модель хорошо ловит «стало вдвое
         короче», когда видит числа, и плохо, когда не видит.
- [x] **Правка типа `rule`, ничего не изменившая, обязана давать «уже
      выполнено», а не «не удалось».** Введён ЧЕТВЁРТЫЙ вердикт `already`
      («требуемое состояние уже в документе»), только для пути `rule`: на
      пути через Редактора пустой дифф остаётся `failed`, там из «операции
      ничего не изменили» не следует, что просьба выполнена. В потоке
      `/edit` идёт как `status: done`, в интерфейсе — пометкой «уже было». Правка 3 (слипшиеся предложения)
      получила `failed` «операции применились, но текст не изменился» —
      потому что типографику по всему документу уже применила правка 2.
      Требуемое состояние в документе ЕСТЬ, и отчёт «не удалось» вводит
      в заблуждение не меньше, чем ложное «сделано» (инвариант 5).
- [x] **Навигатор сваливает в `rule` то, что правилом не является.**
      Промпт Навигатора сужен до двух названных классов плюс отрицательный
      пример (единообразие написания термина — работа Редактора, не правило).
      Фикстурой промпт не доказывается: проверка — приёмочным прогоном.
      Правка 7 (четыре разных написания Bi-encoder → одно) уехала в
      `typography`, код прогнал нормализацию, ничего не изменилось, правка
      потеряна. `rule` обязан ставиться только для трёх названных
      типографских классов; «единообразие термина» — работа Редактора.
- [x] **Глобальные правки получают локальный фрагмент.** Поиск по «ёлочкам»
      из текста правки больше не запасной путь: он идёт ВСЕГДА и сливается с
      адресами Навигатора. Замерено на приёмочном документе: фрагмент правки 8
      вырос с 3 до 9 блоков, ни одна цитата не даёт больше одного блока —
      разрастания нет, ограничитель не нужен. Правки 4 и 14 этим не
      чинятся: в их тексте «ёлочек» нет вовсе. Правки 4, 8, 14
      отказаны с причиной вида «во фрагменте только один случай / этих
      чисел во фрагменте нет», хотя по всему документу случаи есть.
      Формулировка «по всему документу / везде» должна вести к сбору ВСЕХ
      совпадений (операция `replace_all` уже есть), а не к окну ±1 блок.
- [x] **Дыра в безопасности цикла при обрыве связи.** Вызов Проверяющего
      обёрнут: на любом исключении документ восстанавливается из снимка НА
      МЕСТЕ (мутируются те же объекты doc/idx — вызывающий держит старую
      ссылку, вернуть новую пару через исключение нельзя), снимок удаляется,
      исключение поднимается дальше без изменений. Если транспорт
      падает на вызове Проверяющего, патч уже применён к живому `doc`,
      снимок ещё не удалён: исключение улетает наверх, документ остаётся
      изменённым и НЕпроверенным, а временный файл снимка течёт. Нужен
      `try/finally` вокруг проверки в `run_edit`: на исключении — откат из
      снимка и повторный подъём ошибки (ошибка остаётся громкой).

### Ф9. Структура документа (найдено владельцем на показе)

Владелец сравнил наш просмотрщик с LibreOffice: у нас плоская простыня, у
него — заголовки и вложенные списки. Причина измерена: документ размечен
ПРЯМЫМ форматированием, а мы спрашиваем именованный стиль.

`w:pStyle` — 0 штук на весь документ (отсюда «все Normal»), при этом:
`w:outlineLvl` — 24 абзаца (уровень 0 — один, 1 — девять, 2 — четырнадцать);
`w:numPr` — 31 абзац, из них 7 с `ilvl=1`, то есть вложенные, в семи разных
нумерациях; `numbering.xml` в архиве есть. Обычных абзацев без структуры —
61 из 116.

**Это отменяет записанный ниже риск по правке 15.** Формулировка «в
документе НЕТ списков, маркеров списка ноль» — ложная, она получена из
`p.style.name`, а не из XML. Списки есть, вложенность есть. Отказ по
правке 15 остаётся верным, но по ДРУГОЙ причине: в наборе операций нет
смены уровня списка. Прежняя причина была неправдой о документе.

- [x] `parse.py`: блок абзаца получает `level` (из `w:outlineLvl`, иначе
      `None`) и `list` (`{"ilvl","numId"}` из `w:numPr`, иначе `None`).
      Существующие ключи не трогать — на них стоит интерфейс.
- [x] `web/index.html`: заголовки рисуются по уровню, элементы списка — с
      отступом и маркером по `ilvl`. Документ в просмотрщике обязан читаться
      так же структурно, как в LibreOffice.
- [x] `find.outline`: оглавление для Навигатора строится по `level`, а не по
      именам стилей `Heading*`, которых в этом документе нет ни одного —
      Навигатор всё это время работал по плоскому списку вместо 24 заголовков.
- [x] Решить, нужна ли операция смены уровня списка (правка 15). Отдельным
      пунктом ПОСЛЕ трёх верхних: сперва увидеть структуру, потом решать.
      Закрыто Ф15: операция `set_list_level` написана и в контракте.

### Ф10. Работа снаружи (найдено на показе)

- [x] **Поток `/edit` молчит во время правки и его рвёт облачный туннель.**
      Измерено на живом показе: у владельца поток оборвался «TypeError:
      network error» после пятого события. В журнале КОНТЕЙНЕРА при этом
      лежит запись о шестой правке — сервер её доделал, браузер уже не
      получил. Контрольный прогон через тот же туннель с быстрыми правками
      (событие каждые ~4 с) прошёл 22 события за 90 с без разрыва: режет не
      длительность запроса и не объём, а ПАУЗА между байтами. Долгая правка
      (кавычки по десяти блокам) эту паузу и создаёт. Чинится сердцебиением:
      пока считается правка, поток раз в несколько секунд шлёт событие-пинг.
      Клиент неизвестные типы событий игнорирует — интерфейс не трогать.
      Сделано: правка считается в отдельном потоке (`asyncio.to_thread`),
      раз в 5 с уходит `{"type":"ping"}`. Замерено на настоящем uvicorn с
      настоящим сокетом (ASGITransport для этого не годится — он буферизует
      весь ответ): максимальный разрыв между строками 5.0 с.
      Оговорка по истории: код этой правки попал в коммит c73b070 (Ф9) —
      архитектор собрал `git add -A` в общем дереве, пока правка лежала
      несохранённой. Сообщение того коммита её не описывает.
- [x] **`GET /logs` без сессии отдаёт журнал ВСЕХ сессий.** Сервис выставлен
      в интернет без аутентификации: чужие документы, запросы правок и ответы
      модели видны любому. Решение владельца о закрытии — ждём.
