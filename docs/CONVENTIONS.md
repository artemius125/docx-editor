# Соглашения docx-editor

Действующие контракты кодовой базы — то, что не меняется молча. Дополняет
[BUILD_PLAN.md](../BUILD_PLAN.md) (куда идём) и [../CLAUDE.md](../CLAUDE.md)
(инварианты и регламент сессии). Если контракт мешает — меняем контракт
здесь и код одновременно, а не нарушаем молча.

## Мерило

Агент принимает `.docx` и правки обычным языком, вносит их и возвращает
файл плюс отчёт: что сделано, что не вышло и почему. Готовность — НЕ
«N из N выполнено» (недостижимо и не требуется заказчиком), а «по каждой
правке система выдала честный вердикт, и вердикт совпадает с тем, что
реально в файле». Приёмочных корпусов теперь три — оба плоских
(`Архитектура_ColBERT.docx` + `Правки_ColBERT_20.md`, `Математика как
основа.docx`) и один структурный (`bench/fixtures/Регламент.docx` — стили
заголовков, таблица, нумерованный список, жирный текст внутри абзаца), см.
[docs/log/driving-run-2026-07-29.md](log/driving-run-2026-07-29.md) — почему
третий корпус понадобился.

## Конвейер

```
правка (одна из списка)
   │
   ├─ Навигатор  (LLM, ~300 токенов: оглавление + текст правки)
   │     → {kind, rule, ids, anchors, pattern, position, trace}
   │
   ├─ Поиск      (код: якоря/цитаты/pattern/position → блоки → фрагмент с соседями)
   │
   ├─ Редактор   (LLM, ~600 токенов: фрагмент + текст правки)
   │     → патч JSON
   │
   ├─ Валидатор  (код: id есть, old≠new, old найден, без \n-подделки)
   │
   ├─ Применение (код: правка живых lxml-элементов на месте)
   │
   ├─ Проверка следа (код: `trace` — заявленный класс изменения обязан
   │     совпасть со СДЕЛАННЫМ, не с ярлыком Навигатора, см. находку Н66)
   │
   └─ Проверка   (LLM, ~400 токенов: diff изменённых блоков + текст правки,
         пропускается на пути `unify`, где вердикт выносит код)
         → принято | откат снимка + причина
```

Правки типа `rule` (типографика, кавычки) идут мимо Редактора: Навигатор
называет правило, код его выполняет.

**Маршрутизация по классу правки (Ф17–Ф21).** Навигатор относит правку к
одному из четырёх классов, у каждого свой контракт:

1. **`rule`** — типографика (`normalize`), код нормализует, модели нет.
2. **`unify`** — «сделай одинаково по всему документу»: модель ОДИН раз
   выдаёт решение (канон + пары замен), код применяет по всему документу
   и сам выносит вердикт счётом оставшихся вариантов; Проверяющий-LLM не
   зовётся. Не трогает слова, где `_inflects()` истинно (кириллица и не
   ВСЕ-ПРОПИСНЫЕ) — русское словоизменение и подмена слова вместо термина
   не выражаются буквальной заменой (находки Н49, Н62). **Статус маршрута
   НЕ РЕШЁН**: измерен трижды (w13, w14/w15, w16) и ни разу не окупился по
   правилу «прирост меньше трёх ничего не доказывает» — решение принять
   или откатить целиком отложено владельцем до финального прогона, см.
   открытую работу в [BUILD_PLAN.md](../BUILD_PLAN.md) и разбор в
   [docs/log/phase-17-21-routing.md](log/phase-17-21-routing.md).
3. **локальная** (по умолчанию) — Редактор по кластерам соседства;
   правки-переписывания получают рамку «ты автор: `set_text` целого
   абзаца», а не span-хирургию (Ф19). `set_text` сохраняет начертание
   ранов через посимвольное сопоставление старого/нового текста (В3) —
   кроме полностью несвязанных переписываний, там начертание теряется
   целиком (нечего сопоставлять).
4. **`compose`** — правка строит одно целое из разных мест документа
   (таблица из списка, список литературы, сверка далёких абзацев):
   кластеризация выключена, один вызов Редактора со всеми резолвленными
   целями плюс соседи; транзакция и Проверяющий — один на правку, как и у
   остальных путей.

Гвард объёма фрагмента — `_FRAGMENT_CHAR_LIMIT = 15000` знаков (Ф20):
превышение — честный отказ с причиной, Редактор и Проверяющий не
вызываются.

## Контракты (заданы снаружи, не изобретать)

**Блок** — то, что отдаёт `parse.doc_map()` и потребляет веб-интерфейс:
`{"id","kind":"p","style","text","align","level","list","runs":[{"text","b","i","u"}]}`
для абзаца, `{"id","kind":"t","rows":[[...]]}` для таблицы. Формат
зафиксирован `web/index.html` — менять его нельзя, интерфейс переиспользован
из прошлого проекта как есть. `doc_map()` отдаёт только ТЕЛО документа —
колонтитулы в блок не входят и в предпросмотре не видны (см. `field`/
`set_header_footer` ниже).

**Эндпоинты** (тоже из `web/index.html`): `POST /upload`, `POST /edit`
(поток NDJSON), `GET /preview/{session}`, `GET /download/{session}`,
`GET /logs`.

**Событие потока `/edit`**: `{"type":"op","status","text","task","task_text",
"model","at","dt","blocks"}` — плюс `"verdict"`: `"done"` | `"failed"` |
`"rolled_back"` | `"already"` (rule-путь: требуемое состояние уже в
документе) | `"crashed"` (транспорт исчерпал ретраи). Раз в 5 секунд во
время долгой правки уходит `{"type":"ping"}` — сердцебиение против обрыва
потока облачным туннелем (клиент неизвестные типы событий игнорирует).

**Патч** — список операций. Ровно эти 21, новых не изобретать; если правка
не выражается ими, это честный отказ, а не повод дописать операцию:

```
{"op":"replace_text","id":"p12","old":"...","new":"..."}
{"op":"set_text","id":"p12","text":"..."}
{"op":"insert_after","id":"p12","text":"...","style":"Normal"}
{"op":"delete","id":"p12"}
{"op":"move_after","id":"p12","after":"p19"}
{"op":"set_style","id":"p12","style":"Heading 1"}
{"op":"create_table","after":"p57","rows":[[...]],"header":true}
{"op":"set_cell","id":"t3","row":0,"col":1,"text":"..."}
{"op":"normalize","rule":"typography"|"quotes"}
{"op":"replace_all","old":"...","new":"..."}
{"op":"set_list","id":"p12","ilvl":0}
{"op":"set_list_level","id":"p12","ilvl":0}
{"op":"set_format","id":"p12"|"t3","row":0,"col":1,"old":"...","b":true,"i":false,"u":null}
{"op":"insert_row","id":"t3","at":1,"cells":["a","b","c"]}
{"op":"delete_row","id":"t3","row":1}
{"op":"insert_col","id":"t3","at":1,"cells":["a","b","c"]}
{"op":"delete_col","id":"t3","col":1}
{"op":"insert_paragraphs","id":"p12","items":[{"text":"...","style":"Heading 1"},{"text":"...","style":"Normal"}]}
{"op":"footnote","id":"p12","old":"...","text":"..."}
{"op":"field","id":"p12","old":"...","instr":"PAGE"|"NUMPAGES"|"DATE"|"TOC ..."|"REF ... \\h"}
{"op":"set_header_footer","which":"header"|"footer","text":"...","field":"PAGE"}
```

(Исправление при переносе в `docs/`: старый контрактный блок в
`BUILD_PLAN.md` перечислял 19 операций — `set_list_level` и `footnote` там
отсутствовали, хотя обе реализованы, в `patch._OPS` и в `_EDIT_PROMPT`
(находка Н45). Список выше сверен с `docx_editor/patch.py::_OPS` —
21 операция, это авторитетный источник.)

`set_list` создаёт НАСТОЯЩИЙ `w:numPr`, ссылающийся на нумерацию, уже
определённую в `word/numbering.xml` документа (numId выбирает код — первое
определение, — не модель); документ без единого определения нумерации
честно отказывает. `set_list_level` меняет уровень (`ilvl`) уже
существующего элемента списка — на обычном абзаце не работает, это работа
`set_list`.

`set_format`: `row`/`col` — только когда id указывает на таблицу (адресация
ячейки, как у `set_cell`); для абзаца — обычный span по `old`, `row`/`col`
не передаются.

`field`: одна операция на все инструкции поля Word, инструкция — параметр
`instr`, а не отдельная операция на каждый вид поля. `old` необязателен —
без него поле встаёт в конец текста абзаца `id` (нужно для TOC — сначала
`insert_after` пустым абзацем, потом `field` без `old` в него). Простые коды
(PAGE/NUMPAGES/DATE) реализуются `w:fldSimple`, составные (TOC/REF) —
`w:fldChar begin/separate/end` + `w:instrText`; выбор формы делает код по
первому слову `instr`, не вызывающий. Замкнутый словарь пяти кодов — «нет
парсера выражений поля» означает ровно это: switches (`\o "1-3" \h`) код не
разбирает и не проверяет. Значение поля не вычисляется кодом (нет движка
вёрстки) — отчёт операции явно говорит об этом, а не молчит (инвариант 5,
CLAUDE.md).

`set_header_footer`: текст колонтитула целиком и, необязательно, поле в его
конец (тот же набор кодов, что у `field`). Не адресуется id тела документа —
правка видна только в скачанном файле, не в предпросмотре (см. «Блок» выше).
«Первая страница отдельно» и «как в предыдущем разделе» не реализованы —
второй уровень, не просили.

Валидатор отбивает буквальный `\n` в тексте ЛЮБОЙ операции (рекурсивно, по
всем строковым полям, включая списки вроде `cells`/`items`): перевод строки
внутри абзаца — не новый абзац, а подделка того, чего нет в контракте;
несколько абзацев одной операцией — `insert_paragraphs`. Гвард по одному
`\n` не закрывает ВСЕ пути к той же подделке (одинокий абзац-заголовок без
текста — находка Н55) — за это отвечает проверка следа (`trace`) ниже.

**Проверка следа (`trace`, находки Н53/Н55/Н66/Н72).** Навигатор называет
ожидаемый структурный след правки: `null` (обычная текстовая правка, доп.
проверки нет), `"table"`, `"heading"`, `"heading+text"`, `"list"`,
`"footnote"`, `"field"`, `"header_footer"`. Код проверяет СДЕЛАННОЕ — не
итоговое структурное состояние документа относительно ярлыка (этот способ
и был инвертирован, находка Н66: реальные документы несут `w:outlineLvl`
на абзаце независимо от именного стиля, и «переход в заголовок» не
засчитывался, хотя нужная операция реально применилась, находка Н72), а
РЕАЛЬНО ПРИМЕНЁННЫЕ операции этого батча (`_apply_ops` копит их в
`ops_out`, `_trace_error` смотрит на них, не на до/после-диф блоков).
Операция нужного рода среди применённых — след на месте, ярлык не важен,
`done`; нет ни операции нужного рода, ни операции, способной подделать
структуру текстом (`insert_after`/`insert_paragraphs`/`set_text`/…, —
`_CONTENT_FORGE_OPS`) — заявленным классом просто нечего было подделать,
тоже `done` (ярлык неточен, не подделка); отказ остаётся только там, где
подделывающая операция РЕАЛЬНО применилась, а нужная — нет (обе лжи
прогона за рулём — поддельная строка таблицы через `insert_after`,
одинокий заголовок без текста раздела).

## Осознанные границы (решено, не переоткрывать)

Отрезано осознанно, чтобы не повторить утопание первой попытки (3200 строк,
из которых 1800 — демо). Возврат — только через архитектора, с названной
правкой, которая без него не делается:

- Универсальный Document Graph с адаптерами под PPTX/XLSX/LaTeX/HTML.
  Формат один — DOCX, и правится он на месте (инвариант 2, CLAUDE.md).
- Эмбеддинги, BM25, векторный индекс. Поиск — подстрока, regex и нечёткий
  токен-оверлап (`find.locate`, только для навигации, не для мутации): все
  20 правок обоих плоских корпусов имеют лексический якорь.
- Отдельные индексы (Heading/Term/Citation/Formula/Image/Style Index) и
  Semantic Memory. Из всего этого нужна одна функция `first_mention`.
- Планировщик как отдельная модель. Список правок уже структурен, делится
  регуляркой.
- Параллельное исполнение правок. Правки идут по одному документу и видят
  результат предыдущих.
- Резервный провайдер, абстракция под смену модели, ротация логов, Patch
  Engine с разрешением конфликтов и проверкой циклов.
- Каталог операций (progressive disclosure) — при 21 операции порог
  деградации выбора инструментов (20–25, по чужим замерам, Ф14) уже
  вплотную; станет обязательным при переходе за него, раньше — нет.

## Известные риски

- Правки, требующие предметного рассуждения (перепутанные переменные в
  формулах, нотация транспонирования, недифференцируемость через argmax) —
  ожидаемый исход «через раз»; закрывается честным отказом, не мистическим
  успехом.
- `quotes` расставляет ёлочки чередованием внутри абзаца — в чужом
  документе абзац с нечётным числом прямых кавычек сделает непарную
  кавычку открывающей. Косметика, кодом не лечим.
- Поля (PAGE/NUMPAGES/TOC/REF) не имеют вычисленного значения, пока
  документ не открыт и поля не обновлены в Word/LibreOffice (Ctrl+A, F9) —
  в этом окружении `soffice` недоступен, живая проверка рендера не
  проводилась (находка Н58).
- `unify`: не трогает русское словоизменение и слово-вместо-термина
  (`_inflects()`, находки Н49/Н62), но защита стоит только на маршруте
  `unify` — тот же класс порчи ловится и на локальном пути (находка Н69,
  открыто).
