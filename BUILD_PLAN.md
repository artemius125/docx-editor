# План сборки

## Мерило

Агент принимает `.docx` и правки обычным языком, вносит их и возвращает
файл плюс отчёт: что сделано, что не вышло и почему. Готовность считаем
по паре `/home/artem/Загрузки/Правки_ColBERT_20.md` (20 правок) +
`/home/artem/Загрузки/Архитектура_ColBERT.docx` (116 абзацев).

Не «20 из 20 выполнено» — это недостижимо и не требуется заказчиком.
Готовность = по каждой из 20 правок система выдала честный вердикт, и
вердикт совпадает с тем, что реально в файле.

## Конвейер

```
правка (одна из списка)
   │
   ├─ Навигатор  (LLM, ~300 токенов: оглавление + текст правки)
   │     → {kind, rule, anchors}
   │
   ├─ Поиск      (код: якоря → блоки → фрагмент с соседями)
   │
   ├─ Редактор   (LLM, ~600 токенов: фрагмент + текст правки)
   │     → патч JSON
   │
   ├─ Валидатор  (код: id есть, old≠new, old найден)
   │
   ├─ Применение (код: правка живых lxml-элементов на месте)
   │
   └─ Проверка   (LLM, ~400 токенов: diff изменённых блоков + текст правки)
         → принято | откат снимка + причина
```

Правки типа `rule` (типографика, кавычки) идут мимо Редактора: Навигатор
называет правило, код его выполняет.

### Ф2. Патч и валидатор
- [x] `patch.py`: `validate(blocks, op, doc) -> None | текст ошибки` и
      `apply(doc, idx, op) -> описание`. Валидация ДО применения:
      несуществующий id, `old == new`, `old` не найден в блоке, неизвестный
      стиль (в ошибку — список доступных стилей документа).
- [x] Операции из контракта выше, кроме `normalize` (она в Ф3).
      Правка текста — через раны, форматирование абзаца сохраняется.
- [x] Демо: каждая операция применяется; каждый вид невалидного патча
      отбивается валидатором с внятным текстом.

  Находка: `validate` в итоге принимает три аргумента — `(blocks, op, doc)`,
  а не два. Причина: список «доступных стилей абзацев» для ошибки
  `set_style` должен браться из `doc.styles` (полный каталог стилей,
  определённых в документе), а не из `blocks` — там только стили, УЖЕ
  применённые к каким-то абзацам. Проверено на реальном документе:
  `Архитектура_ColBERT.docx` использует только `Normal` во всех 116
  абзацах (см. Ф1), но в `doc.styles` определён `List Paragraph` (и НЕТ
  `List Bullet`) — без доступа к `doc` эта проверка невозможна в принципе.
  Контракт-строка выше в этом файле поправлена соответственно.

  Ревью архитектора нашло три дефекта, все починены: (1) `_ptext`/
  `_replace_span` ходили только по ранам верхнего уровня (`r_lst`) — текст
  внутри `w:hyperlink` выпадал, из-за чего `apply` видел офсеты, не
  совпадающие с `p.text` (то, что видит `validate`), и молча портил абзац;
  теперь обход через `p_el.iter(qn("w:r"))`, плюс громкая ошибка при
  недостижимом отрицательном смещении. (2) `insert_after` с несуществующим
  стилем проходил `validate` и падал `KeyError` в `apply` — вынесена общая
  проверка стиля `_style_error`, теперь зовётся и из `set_style`, и из
  `insert_after`. (3) `create_table` строил таблицу без рамок (в контракте
  нет поля `style`, а из именованных стилей часто есть только `Normal
  Table`) — рамки теперь ставятся всегда прямо в XML (`_add_borders`,
  `w:tblBorders`). Демо дополнено тремя проверками (гиперссылка, плохой
  стиль в `insert_after`, `w:tblBorders` в XML), все падают при регрессии.

### Ф3. Правила без модели

Числа ниже замерены архитектором на `Архитектура_ColBERT.docx` — это
приёмочные значения, а не ориентиры.

- [x] `rules.py`: `typography` — три правила по всему документу:
      - пробел перед пунктуацией: любой пробельный, включая U+00A0
        (в документе 6 мест перед двоеточием, и все шесть — именно U+00A0,
        обычных нет ни одного; плюс 1 место перед закрывающей скобкой);
      - пропущенный пробел после точки между предложениями. Правило:
        **слева буква ЛЮБОГО регистра, справа заглавная**; от ложных
        срабатываний защищает запрет цифр по обе стороны от точки, а не
        регистр. Так надо, потому что из трёх случаев в документе
        («в RAG.Усредненный», «процесс.Исследователи», «напрямую.В основе»)
        первый имеет слева ЗАГЛАВНУЮ `G`, и правило «слева строчная»
        пропустило бы треть случаев молча. Ложные срабатывания здесь —
        только десятичные числа (`4.2`, `0.4448`), их и отсекаем;
      - невидимые U+2060/U+200B/U+FEFF/U+00AD — вырезать. В документе их
        ноль, живого случая нет: демо для этого правила — на синтетике.
- [x] `quotes` — прямые кавычки в ёлочки (в документе 22 прямых при 13
      парах уже готовых ёлочек; вложенных кавычек внутри ёлочек нет).
- [x] Демо на реальном `Архитектура_ColBERT.docx`: после `typography`
      не осталось ни одного пробела перед пунктуацией и все 3 слипшихся
      предложения разделены, при этом 6 десятичных чисел (`4.2%`, `0.4448`,
      `0.4436`, `8.8`, `36.2%`, `6.7%`) не тронуты; после `quotes` прямых
      кавычек 0, а 13 исходных пар ёлочек целы.

  Находка: `rules.py` импортирует `_ptext`/`_replace_span` из `patch.py` (не
  дублирует их), а `patch.py` вызывает `rules.typography`/`rules.quotes` из
  `_op_normalize` — прямой импорт на верхнем уровне модуля дал бы цикл, поэтому
  импорт `rules` внутри `patch._op_normalize` сделан ленивым (внутри функции).
  Числа архитектора (7 пробелов = 6 U+00A0 перед `:` + 1 перед `)`; ровно 3
  слипшихся предложения теми же тремя строками; 6 десятичных чисел встречаются
  по одному разу; 22 прямых кавычки, 13 исходных пар ёлочек) перепроверены на
  реальном файле до написания кода — совпали ровно, расхождений нет.

### Ф4. Поиск

Ставка «поиска подстрокой хватит» проверена архитектором на всех 20
правках: якорь нашёлся у каждой, провалов ноль — эмбеддинги не нужны.
Но качество якоря решает всё: обобщённый термин даёт мусор («MaxSim» →
25 блоков из 116), а дословная цитата из формулировки правки схлопывает
выборку до одного-четырёх («размерностью m × n» → 1, «ColBERT-Att» → 4,
«Эффективность архитектур: Сравнительный анализ» → 1). Отсюда требование
к Навигатору в Ф5: якорь — самая специфичная ДОСЛОВНАЯ цитата из текста
правки, а не термин своими словами.

- [x] `find.py`: `by_text(blocks, needle)`, `by_regex(blocks, pattern)`,
      `first_mention(blocks, term)` (для «расшифруй при первом упоминании»),
      `outline(blocks)` (заголовки + первые слова абзацев верхнего уровня,
      для контекста Навигатора), `fragment(blocks, ids, around=1)`.
- [x] Демо: фикстура из 20 наборов якорей (по одному на каждую правку) —
      для каждого поиск находит непустой набор блоков, и он не больше 20.

  `outline`: в приёмочном документе заголовков нет вовсе (все 116 абзацев
  стилем Normal — см. Ф1), поэтому оглавление устроено как id + обрезанный
  до 20 знаков префикс текста для обычных абзацев (Heading*/Title — целиком,
  на будущее для других документов). На `Архитектура_ColBERT.docx` даёт
  2972 знака на 116 блоков — заведомо укладывается в промпт Навигатора
  (~300 токенов по бюджету конвейера).

  Находки по ходу фикстуры (20 якорей из `Правки_ColBERT_20.md`, все
  проверены на реальном `Архитектура_ColBERT.docx`):

  1. В документе U+00A0 встречается не только перед пунктуацией (это уже
     фиксировала Ф3), а вообще между случайными словами середины
     предложения — например `Оператор\xa0$\top$\xa0представляет`,
     `как\xa0и,`, `секундами\xa0)`. Дословная цитата из правки, набранная
     обычными пробелами, не матчится как подстрока, если задевает такую
     границу. Якоря для правок 1, 2 и 17 пришлось обрезать ДО первого nbsp
     в цитате, а не после — иначе `by_text` возвращает пустой список на
     формально «дословной» цитате.

     Ревью архитектора замерило масштаб точно: **61 из 116 абзацев
     содержат U+00A0 внутри предложения, 147 вхождений всего** — это
     большинство документа, а не редкая ловушка, и она бьёт дважды:
     в якорях Навигатора и в поле `old` операций `replace_text`/
     `replace_all`. Промптом не лечится — модель не видит разницы между
     обычным пробелом и U+00A0 в тексте, который ей показывают. Починено
     в коде, в одном месте: `find._flex_span(haystack, needle)` — сначала
     точный `str.find` (быстрый путь, точные совпадения не меняются),
     и только при промахе needle режется по пробельным разрывам
     (`re.split(r"\s+", needle)`) и собирается в regex, где любой такой
     разрыв матчится с любым другим (`\s` в Python уже покрывает U+00A0).
     Публичный `find.flex_find` отдаёт индекс начала; `_flex_span` — ещё и
     конец РЕАЛЬНОГО совпадения, а не `start + len(needle)`: разрыв в
     документе может быть длиннее или короче того, что в needle.

     `by_text` использует `flex_find`. `patch.validate` (проверка «текст
     не найден» для `replace_text`/`replace_all`) и `patch._op_replace_text`/
     `_op_replace_all` (реальное вычисление спана для замены) используют
     ОДНУ и ту же `_flex_span` из `find.py` — не дублируют её и не могут
     разойтись, это именно тот класс бага, что уже портил гиперссылки в Ф2.
     Демо: `patch_demo.test_replace_text_tolerates_nbsp` — абзац
     `"слово\xa0слово синее небо."`, `old` набран обычным пробелом,
     результат проверен целиком (не только начало), плюс отдельно проверено,
     что точное совпадение (быстрый путь) не сломано; `find_demo.
     test_by_text_tolerates_nbsp` — та же цитата про `Оператор`, что и в
     примере архитектора, находит `p31` через обычные пробелы.
  2. Формулы — отдельная ловушка: правка 16 цитирует «размерностью m × n»
     (юникодный знак умножения, как выглядит в размеченном тексте правки),
     а в документе это `$m \times n$` (сырой LaTeX-макрос, буквально
     обратный слэш и `times`). Подстрокой это не совпадает никогда. Якорь
     для правки 16 взят из текста ДО формулы («матричных умножений
     MaxSim»), не из самой формулы.
  3. У трёх правок из 20 в тексте самой правки нет ни одной дословной
     цитаты документа — это не промах `find.py`, а честная граница метода:
     - правка 6 (кавычки в ёлочки) — глобальное типографическое правило,
       оно и не должно идти через `find`: Навигатор называет `rule`, код
       применяет его по всему документу (см. «Конвейер» — правки типа
       `rule` идут мимо Редактора);
     - правка 9 («заголовок документа») — правка по позиции, а не по
       тексту: цель — первый блок документа, а не что-то, что можно
       процитировать;
     - правка 15 (вложенные характеристики в списке) — это уже описанный
       выше в «Известных рисках» невыполнимый случай (в документе нет
       списков вообще); отсутствие цитаты — ещё один взгляд на ту же
       находку архитектора, не новая проблема.
     Демо фиксирует именно эти три номера явным `assert`, чтобы если
     список изменится при доработке — это было явным сигналом регрессии,
     а не тихо пропавшей проверкой.

### Ф5. Цикл правки

Оба вызова модели архитектор проверил живьём на Gemma 4 26B до написания
кода. Результаты ниже — измеренные, промпты в них уже отлажены.

**Проверяющий работает и это подтверждено.** Четыре случая по правке 11,
все четыре вердикта верны: правка сделана верно → `ok=true`; сделано
наоборот (ровно тот провал, на котором соврал прошлый проект) → `ok=false`
«выполнена наоборот»; пустышка `old==new` → `ok=false` «правка не
выполнена»; изменён не тот термин → `ok=false`. 0.01–0.02 ₽ за проверку.
Асимметрия «проверять легче, чем делать» на 26B держится — на ней и стоит
обещание честного отчёта.

**Навигатор ошибается, и конвейер обязан это переживать.** На шести
представительных правках сырой промпт дал 2 верных ответа из 6,
отлаженный — 5 из 6. Что дало разницу и должно попасть в реализацию:

- В ответе есть поле `ids` рядом с `anchors`: `{"kind","rule","ids","anchors"}`.
  Модель и так пытается называть блоки, но без этого поля засовывает id
  внутрь цитаты (`"p51 Bi-Encoders (Dense Embeddings)"`), и якорь не
  находит ничего. С отдельным полем правка 19 дала 3 верных блока вместо
  нуля. Плюс защита в коде: срезать ведущий `pNN ` из якоря.
- Правила описаны конкретикой, а не названием: «лишний пробел перед
  двоеточием / точкой с запятой / закрывающей скобкой», «слипшиеся
  предложения», «невидимые символы» — иначе правка 2 не опознаётся как
  `typography` и уходит к модели вместо кода.
- `global` запрещено использовать как свалку: «если можешь назвать хотя бы
  один id — это не global, а local». Без этой фразы правка 9 падала в
  `global` и теряла адрес.
- Якоря рядом с формулами цитируют прозу, а не формулу: правка 16 пишет
  `m × n`, а в документе лежит `$m \times n$` — это никогда не совпадёт.

      не нашёл — код ищет сам по дословным цитатам из формулировки правки

- [x] `llm.py`: один вызов модели, `.env`, JSON-режим, разбор ответа.

- [x] `edit.py`: Навигатор → поиск → Редактор → валидатор → применение →

      перечитать документ из копии. Максимум две попытки, потом честный
      отказ с причиной.
- [x] `split(request)` — детерминированное деление списка правок по
      markdown-нумерации (перенести из прошлого проекта, он там работал).
- [x] Демо: правка 11 из файла правок проходит и не делает `old == new`;
      заведомо невыполнимая правка («поставь нумерацию страниц») даёт
      честный отказ и не трогает документ.

  Находки по ходу (задание строителю уточнило детали демо по сравнению с
  формулировкой выше — задокументировано, а не переоткрыто):

     стабильно возвращает `p76`), у 11 такого измерения для связки
     Навигатор+Редактор не было (архитектор измерял для неё только
     Проверяющего, отдельно, четырьмя фейковыми диффами). Прогнано дважды
     подряд — оба раза `verdict=done`, `p76` реально меняется. Отказ
     («поставь нумерацию страниц») в демо проверен БЕЗ живого вызова —
     фейковым Навигатором, который целится в несуществующий `id` и
     промахивающийся якорь, а текст правки несёт `«цитату»`, которой тоже
     нет в документе. Это бьёт ровно в требуемый путь кода (резолв →
     запасной поиск по «ёлочкам» → пусто → честный отказ), просто без
     траты вызова модели и без риска, что конкретно «нумерация страниц»
     когда-нибудь случайно попадёт в `ops` живого Редактора.
  2. Найден живой баг Редактора: на 26B модель иногда кладёт в `"ops"`
     посторонний примитив первым элементом рядом с валидными операциями
     (`{"ops": [0, {"op": "replace_text", ...}, {"op": "replace_text", ...}]}`
     — воспроизведено на правке 12). `patch.validate` ожидает словарь и
     падал `AttributeError` на `0.get`. Почин в `edit.py`: `_clean_ops`
     отбрасывает элементы `ops`, которые не словари, ДО `validate` — это
     не проглатывание ошибки (инвариант 6), а нормализация плохо
     сформированного, но частично разбираемого ответа модели перед тем,
     как код станет его проверять по существу.
  3. Поле `kind` в ответе Навигатора (`"local"|"global"`) в код маршрутизации
     не заведено намеренно: оно не упоминается в разделе «Routing» задания
     буквально (там ветвление только по `rule`/`ids`/`anchors`), а
     дисциплинирующий эффект («если можешь назвать хоть один `id` — это
     local, а не global») достигается формулировкой в промпте Навигатора,
     а не отдельным `if kind == ...` в коде. `kind` разбирается из ответа,
     но не влияет на резолв: полноценная отдельная ветка ради поля,
     которое ничего не решает, была бы абстракцией с одним вызывающим.
  4. Снимок для отката не требует пути исходного файла на диске: `doc` —
     объект `python-docx` в памяти, поэтому `_snapshot`/`_restore` в
     `edit.py` используют `tempfile.mkstemp` + `doc.save()`/`Document()`
     сами по себе, без параметра `path` в `run_edit`. Побочный эффект,
     который стоит явно отметить: живой прогон демо ни разу не пишет
     поверх `/home/artem/Загрузки/Архитектура_ColBERT.docx` — документ
     только читается один раз в память, а откат/снимок работают через
     временный файл, так что мерило приёмки не портится повторными
     запусками `run_all.py`.
  5. Ф5 переоткрывалась на Ф6 и починена там же (два дефекта, оба вскрыты
     журналом из Ф6 — поле `reply` окупилось в первый же прогон):
     - Навигатор вернул `ids: [112]` ЧИСЛОМ, а не `"p112"`. `_resolve`
       сравнивал с множеством строк и молча терял id, резолв выживал только
       на якоре и уезжал не туда. Это тот же класс, что и «id внутри цитаты»:
       каноническую форму id приводит КОД, а не промпт. Добавлен
       `_normalize_id` (голое число → `pNN`, регистр вниз), сверка с
       реальными id осталась строгой — фаззи-совпадений не заводить.
     - Живое демо требовало `verdict == "done"` от 26B, то есть краснело от
       настроения модели. По «Мерилу» готовность — честный вердикт,
       совпадающий с файлом, а не «сделано»: теперь `done` обязан означать
       реальное изменение p76, а `failed`/`rolled_back` — нетронутое
       содержимое и непустую причину. Байтовое сравнение `.docx` для этого
       НЕ годится: `python-docx` пишет zip через `writestr`, тот штампует
       записи текущим временем, и один и тот же документ даёт разные байты
       (измерено). Сравнивается содержимое блоков через `_btext`.

### Ф8. Находки приёмки (по порядку важности)

- [x] **Обрезание абзаца проходит как `done` — единственная найденная ложь
      отчёта.** Правка 18 (`p35`): модель выдала `set_text`, укоротив абзац
      с 456 до 332 знаков и оборвав последнее предложение буквальным «…»
      («…winner-takes-all) карди…»). Смысловая часть правки сделана верно,
      поэтому Проверяющий сказал `ok`, а машинная сверка «содержимое
      изменилось» такое не ловит по устройству. Это потеря текста, выданная
      за успех. Чинить двумя независимыми слоями:
      1) детерминированно в `patch.validate` — запретить `set_text`/
         `replace_text`, где `new` оканчивается многоточием, а `old` нет
         (в приёмочном документе таких абзацев 0, ложных срабатываний нет);
      2) показывать Проверяющему длины: в диффе к каждому блоку добавить
         «было N знаков, стало M» — модель хорошо ловит «стало вдвое
         короче», когда видит числа, и плохо, когда не видит.
- [x] **Правка типа `rule`, ничего не изменившая, обязана давать «уже
      выполнено», а не «не удалось».** Введён ЧЕТВЁРТЫЙ вердикт `already`
      («требуемое состояние уже в документе»), только для пути `rule`: на
      пути через Редактора пустой дифф остаётся `failed`, там из «операции
      ничего не изменили» не следует, что просьба выполнена. В потоке
      `/edit` идёт как `status: done`, в интерфейсе — пометкой «уже было». Правка 3 (слипшиеся предложения)
      получила `failed` «операции применились, но текст не изменился» —
      потому что типографику по всему документу уже применила правка 2.
      Требуемое состояние в документе ЕСТЬ, и отчёт «не удалось» вводит
      в заблуждение не меньше, чем ложное «сделано» (инвариант 5).
- [x] **Навигатор сваливает в `rule` то, что правилом не является.**
      Промпт Навигатора сужен до двух названных классов плюс отрицательный
      пример (единообразие написания термина — работа Редактора, не правило).
      Фикстурой промпт не доказывается: проверка — приёмочным прогоном.
      Правка 7 (четыре разных написания Bi-encoder → одно) уехала в
      `typography`, код прогнал нормализацию, ничего не изменилось, правка
      потеряна. `rule` обязан ставиться только для трёх названных
      типографских классов; «единообразие термина» — работа Редактора.
- [x] **Глобальные правки получают локальный фрагмент.** Поиск по «ёлочкам»
      из текста правки больше не запасной путь: он идёт ВСЕГДА и сливается с
      адресами Навигатора. Замерено на приёмочном документе: фрагмент правки 8
      вырос с 3 до 9 блоков, ни одна цитата не даёт больше одного блока —
      разрастания нет, ограничитель не нужен. Правки 4 и 14 этим не
      чинятся: в их тексте «ёлочек» нет вовсе. Правки 4, 8, 14
      отказаны с причиной вида «во фрагменте только один случай / этих
      чисел во фрагменте нет», хотя по всему документу случаи есть.
      Формулировка «по всему документу / везде» должна вести к сбору ВСЕХ
      совпадений (операция `replace_all` уже есть), а не к окну ±1 блок.
- [x] **Дыра в безопасности цикла при обрыве связи.** Вызов Проверяющего
      обёрнут: на любом исключении документ восстанавливается из снимка НА
      МЕСТЕ (мутируются те же объекты doc/idx — вызывающий держит старую
      ссылку, вернуть новую пару через исключение нельзя), снимок удаляется,
      исключение поднимается дальше без изменений. Если транспорт
      падает на вызове Проверяющего, патч уже применён к живому `doc`,
      снимок ещё не удалён: исключение улетает наверх, документ остаётся
      изменённым и НЕпроверенным, а временный файл снимка течёт. Нужен
      `try/finally` вокруг проверки в `run_edit`: на исключении — откат из
      снимка и повторный подъём ошибки (ошибка остаётся громкой).

## Чего в этом проекте нет (решено, не переоткрывать)

Отрезано осознанно, чтобы не повторить утопание первой попытки. Возврат
к любому пункту — только через архитектора, с названной правкой, которая
без него не делается.

- Универсальный Document Graph с адаптерами под PPTX/XLSX/LaTeX/HTML.
  Формат один — DOCX, и правится он на месте.
- Эмбеддинги, BM25, векторный индекс. Поиск — подстрока и regex: все 20
  правок имеют лексический якорь, документ 35 тыс. знаков.
- Отдельные индексы (Heading/Term/Citation/Formula/Image/Style Index) и
  Semantic Memory. Из всего этого нужна одна функция `first_mention`.
- Планировщик как отдельная модель. Список правок уже структурен,
  делится регуляркой.
- Параллельное исполнение правок. Правки идут по одному документу и видят
  результат предыдущих.
- Резервный провайдер, абстракция под смену модели, ротация логов,
  Patch Engine с разрешением конфликтов и проверкой циклов.
